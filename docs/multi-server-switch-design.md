# 多服务器快速切换 · 设计方案

> 状态：**设计稿**（2026-10-18）。基于对当前实现的代码走查，非凭空设想。
> 目标：让「我在 A 电脑上，想切到 B 电脑」这件事在手机上**少点几下、少等几秒、少丢状态**。

## 一、现状（代码事实）

### 数据层（`SshConfig.kt`）

| 存储键 | 内容 | 说明 |
|---|---|---|
| `ssh_json` | **当前生效**的那一条 `SshConfig` | 隧道、复用指纹、表单预填都只认它 |
| `ssh_hosts_json` | 全部主机的列表 | 逐条容错解析 |
| `ssh_active_host` | 当前主机的 id | 与 `ssh_json` 冗余，用于下拉定位 |

`SshConfig` 字段：`id / name / host / port / user / remoteHost / remotePort / authType / password / keyPath / keyPass`。

**关键设计**（注释里写明的分工）：切换主机 = 把选中那条写进 `ssh_json`，下游一个字都不用改。这个抽象很干净，本方案沿用。

`fingerprint()` 的输入**刻意不含 `id`/`name`** —— 改显示名不该让隧道重建，这个细节设计得对。

### 切换链路（`MainActivity.kt` ~1296-1418）

```
用户在网页上
  → 点「回连接屏」（或断开后自动回）
     → 找到并展开「连接设置」表单
        → 打开「主机」下拉（第 0 项固定是「＋ 新建主机…」）
           → 选中目标主机 → applyHostToForm + setActive
              → 若原本已连：disconnectCurrent()
                 → waitTunnelReleasedThen(2000)  ← 等隧道真的释放，超时 2s
                    → connectAction() → ensureTunnel → 拨号 → 播种 token → 加载页面
```

### 三条硬约束（本方案必须遵守）

**① 隧道是严格单例**

```kotlin
/** 当前 SSH 隧道（唯一实例）。 */
var sshTunnel: SshTunnel? = null   // private set，只由 ensureTunnel/closeTunnel 改
/** 串行化拨号（同一时刻只允许一条）。 */
private val dialLock = Any()
```

`ensureTunnel` 在指纹不匹配时会先把 `sshTunnel` 置空并 `obsolete.close()`，**再**拨新号。
所以「预先建好 B 的隧道、切换时直接换过去」在当前架构下**不可能** —— 除非改隧道层（见 §四 方案 B）。

**② 指纹不同 = 必须重建**

切换主机意味着 `host/user/password` 至少一项变化 → `fingerprint()` 必变 → 必然重新拨号。
不存在「切到 B 还复用 A 的隧道」这种可能。

**③ 端口漂移会改变 origin**

`PORT_CANDIDATES` 首选 3080，被占则退到 13080。注释明确记过实测：残留 dbclient 占着 3080 时
会漂到 13080，**origin 随之改变，cookie/localStorage 全换一份**。
所以切换时必须等旧隧道**真的**释放（现有 `waitTunnelReleasedThen` 就是为此），否则不只是慢，还会丢登录态。

### 耗时构成（代码里的实测标注）

| 环节 | 量级 | 来源 |
|---|---|---|
| `close()` 收旧进程 | 每进程最多 1.5s，`CLOSE_JOIN_MS` 上限 5s | `DshApp` 常量 |
| `waitTunnelReleasedThen` | 上限 2000ms | 切换链路 |
| 拨号 | **成功 ~1-3s**；失败最坏 `3 × 15s` | `DshApp.ensureTunnel` 注释 |
| 页面加载 | 未测量 | — |

**注意**：以上是源码里的标注，**不是我在真机上秒表量出来的**。真正定方案前应该实测一次端到端（见 §五）。

## 二、问题拆解

把「快速切换」拆成两个独立的问题，**它们的解法完全不同**：

| 问题 | 性质 | 能否靠本 App 解决 |
|---|---|---|
| **A. 导航太深** —— 网页 → 连接屏 → 展开表单 → 下拉 → 选 | 交互/UI | ✅ 完全可控 |
| **B. 切换要重拨并重载页面** —— 秒级等待 + 页面状态丢失 | 架构 | ⚠️ 只能优化感知，不能消除（受约束①②③） |

**先做 A，收益立竿见影且零风险；B 只做「让等待可预期」，不做架构改动。**

## 三、方案 A（推荐，可分批落地）

### A1. 网页态加「切换主机」常驻入口

**问题**：切主机必须先回连接屏，而回连接屏要经过断开横幅或 BACK —— 路径深且不确定。

**改法**：网页态顶部加一个主机入口（与既有的「已连上电脑」状态条同层），点开直接出主机列表；
选中即切换。

**关键约束**：入口要**轻**。网页态顶部空间在手机上极紧张（第二十一节实测：384px 视口下头部各项已很挤），
所以入口本身不该占新的一行 —— 建议复用现有状态条/标题行右侧的位置，或做成长按。

**取舍**：不引入注入（本项目已定零注入），所以这个入口只能做在 **App 的原生层**，不能盖在网页上。
那就是一个原生悬浮按钮或原生工具条 —— 会遮挡网页内容，需要在真机上权衡位置。

### A2. 主机列表升级为「底部弹层」，带状态与延迟读数

**问题**：现有是 Spinner 下拉，只能显示名字；用户选之前不知道那台机器现在通不通。

**改法**：换成底部弹层（BottomSheet 风格），每行显示：

| 列 | 内容 | 数据来源 |
|---|---|---|
| 名字 | `config.label` | 已有 |
| 地址 | `user@host:port` | 已有 |
| **上次连接结果** | 「3 秒前连过 ✓」/「上次失败」/「未连过」 | **需要新增**：每次拨号结果写回该主机的记录 |
| 快捷操作 | 编辑 / 删除 / 设为默认 | 已有（编辑/删除）；「默认」是新增语义 |

「上次连接结果」这一条是本方案**信息量最大**的新增：手机上切主机最常见的失败原因是「那台机器没开机/不在同一网络」，
而用户在选择时无法预知，只能试一次才知道 —— 每次都浪费一次拨号（最坏 45s）。

**需要新增的持久化**：每条主机记 `lastOkAt` / `lastError`。放在 `SshConfig` 里会污染「配置」语义
（而且 `fingerprint()` 要排除它），更干净的做法是**单独的 `ssh_host_health_json`**：`{ id: {okAt, errKind} }`。

### A3. 切换确认与「正在切换」的明确反馈

**问题**：切换时页面会重载，但现有反馈只有状态条上几行字；用户容易以为卡住而反复点。

**改法**：切换期间显示一条**不可被 BACK 弄没的**进度层，明确写：

```
正在切换到 B 电脑…
  ① 断开 A          ✓
  ② 建立连接        ⋯
  ③ 加载页面
```

现有 ①②③ 引导流程已经有这套结构（`ConnectDecisions.showProgress` 就是这个判据），切换时直接复用，
**不要新造一套**。

### A4. 记住「上次用的主机」并预选

`SshHosts.activeId` 已经持久化了，但只用于下拉定位。建议：App 冷启动进连接屏时，
表单直接预填 active 主机（已有），并把主按钮文案改成 `连上 B 电脑并打开网页`（把 `label` 塞进文案）——
让用户一眼确认「我要连的是哪台」，避免连错。

### A5. 失败后的「换一台」快捷动作

连接失败时（`connectFailed`），除了现有的重试，再给一个**一键切到下一台**的动作。

这对「我有多台机器，不知道哪台开着」的场景是决定性的 —— 把 N 次「回连接屏→下拉→选」压缩成 N 次点击。

## 四、方案 B（不进本期，留作备选）：让切换真的更快

要让「切换」从秒级降到即时，必须突破约束①（隧道单例）。两条路：

### B1. 隧道池（预热 B 的隧道，切换时提升为当前）

**做法**：把 `sshTunnel: SshTunnel?` 改成「当前 + 备用」两槽，在用户停留于 A 时后台悄悄为
「最可能切换的目标」建好隧道，切换时直接提升。

**为什么现在不能做**：

1. `ensureTunnel` / `closeTunnel` / `dialGeneration` / `pendingClose` / 看门狗**全部假设单例**，
   改动面覆盖隧道层核心，回归风险高；
2. **端口冲突**：两条隧道都想要 3080，第二条必然漂到 13080 → origin 变化 → 登录态丢失，
   「快」换来的是「要重新登录」，得不偿失；
3. 手机上是**内存与电量**敏感场景，常驻第二条 SSH 隧道 + dbclient 进程的代价需要实测。

**结论**：除非 ① 端口策略先改成「每条隧道固定独占一个候选端口且 origin 稳定」，否则 B1 不值得做。

### B2. 会话保持（切回来时不丢页面状态）

**做法**：为每个主机的 WebView 保留独立状态（cookie / localStorage 按 origin 已天然隔离，
因为端口不同即 origin 不同），切换时不销毁 WebView 而是保留多份。

**代价**：手机上多份 WebView 的内存开销很大（Chromium 每份都不小），且当前 `retainedWebView` 是单份设计。

**结论**：只在「用户确实频繁来回切」时才值得，且需要先测内存。

### B3. 减少重拨（只对同一台机器的配置微调有效）

`fingerprint()` 已排除 `id`/`name`，所以改显示名不重建 —— 这个已经做对了。
可再考虑把 `password` 从指纹里拿掉（改成连接时校验，失败再重建），但**风险高**：
密码变了却不重建会连不上且难排查。**不建议改**。

## 五、落地前必须先量的事（真机）

本设计有**一个未测量的关键数字**：端到端切换到底多久。方案 A 与 B 的分界完全取决于它：

- 若「断旧 + 拨新 + 加载」总耗时 < 2s：**方案 A 足够**，用户感知的是「点了就切」，B 不值得做；
- 若 > 5s：需要认真考虑 B1/B2，或至少要给足进度反馈。

**测量方法**（已有工具，无需新写）：

```sh
# App 需为 debug 版（release 不可调试）
PID=$(adb shell ps -A | grep dshhandheld | awk '{print $2}')
adb forward tcp:9222 localabstract:webview_devtools_remote_$PID

# 切换前后各记一次时间戳，读 DiagLog 里的关键行
adb logcat -c && adb logcat | grep -E "多主机|ensureTunnel|拆掉旧隧道|已建立"
```

要抓的四个时刻：`切到 <label>` → `拆掉旧隧道` → `已建立 <baseUrl>` → 页面 `onPageFinished`。

**注意隐私**：切换会中断当前隧道，若 App 正连着你在用的 harness 会话，会打断它。实测请用一次性的测试会话。

## 六、建议的落地顺序

| 期 | 内容 | 风险 | 依赖 |
|---|---|---|---|
| **1** | A2 弹层（含「上次连接结果」）+ A4 预选与文案 | 低 | 新增 `ssh_host_health_json` |
| **2** | A3 切换进度层（复用现有 ①②③） | 低 | 无（纯 UI） |
| **3** | A5 失败后「换一台」 | 低 | 依赖 A2 的健康数据 |
| **4** | A1 网页态入口 | **中**（会遮挡网页，需真机权衡） | 需先决定入口形态 |
| **5** | 实测端到端耗时，据此决定是否启动 B | — | 真机 |

**第 1 期就能解决大部分「切换太麻烦」的抱怨**，且完全不碰隧道层 —— 这是本方案刻意的取舍：
先把可控的部分做到位，把不可控的部分（重拨）用**可预期的反馈**覆盖住。

## 七、明确不做的

- ❌ **注入网页做切换 UI** —— 本项目已定零注入（2026-10-18 决定），且注入被宿主升级反复打断的先例已有两次。
- ❌ **改 `SshConfig.fingerprint()` 的字段集合** —— 现设计已考虑周全（排除 name，含全部连接参数），改动只会引入难排查的故障。
- ❌ **B1 隧道池（本期）** —— 端口/origin 冲突未解决前，做了反而更差。
