# 缩放实验记录（2026-10-30）

> 本文件是「判定 dsh web 在手机上的可读性瓶颈层级」这一题目的**实验记录**：
> 观测条件、仪器校准、结果、假设判定、决策，以及**尚未完成的部分**。

## 1. 要回答的唯一问题

在零注入约束下，384 CSS px 视口上的可用性不足属于哪一层，且**把缩放设成 0.75
是「看到更多内容」还是「仅仅把页面画小」**。

## 2. 观测条件（已固定）

| 项 | 值 |
|---|---|
| 引擎 | 本机 Google Chrome（Blink），headless |
| 视口 | 384×832 / 512×832 / 768×832（CDP `Emulation.setDeviceMetricsOverride`） |
| dpr | 3.75（前两组）、1.0（768 组） |
| 页面 | 真实 dsh web（`http://127.0.0.1:3080/?token=…`，303 换 cookie） |
| 缩放档 | 1 / 0.9 / 0.85 / 0.8 / 0.75 / 0.5 / 1.25 / 1.5 |

工具：`tools/zoom-harness.mjs`（编排）+ `tools/web-zoom-probe.mjs`（测量）
门禁：`tools/check-zoom-metrics.py`　存档：`docs/measurements/*.json`

## 3. 仪器校准：先证明尺子是准的

第一次跑出来的数是**假的**，两个 bug 都被门禁的「仪器自证」抓到：

1. **target 错配**：编排脚本每次重新 `GET /json/list` 取 `list[0]`，而 probe 是另一次调用
   —— 可能选中另一个 target。实测读到 `innerWidth=780`（≈800 减滚动条），不是模拟的 384。
   修：解析一次并缓存 ws。
2. **模拟随会话失效**：CDP 的 `setDeviceMetricsOverride` 在**发起它的会话断开时被清除**。
   编排脚本设完就关会话，probe 再连上去时页面已退回默认窗口。
   修：**谁测量谁拥有会话** —— 让 probe 自己设观测条件。

校准方法：用同款 `viewport` meta 的最小样例页面，确认 `setPageScaleFactor` 对
`visualViewport.scale` 的影响方向。校准结果（这一步在真实页面上重复得到了同样结论）：

| 请求 | 样例页实际 | 真实 dsh 页实际 |
|---|---|---|
| 0.9 | 1.0 | 1.0 |
| 0.75 | 1.0 | 1.0 |
| 0.5 | 1.0 | 1.0 |
| 1.25 | — | **1.25** |
| 1.5 | **1.5** | **1.5** |

## 4. 结果

### 4.1 缩放语义：缩小被钳制，放大有效

```
384 宽: 1->1   0.75->1(钳)   1.25->1.25   1.5->1.5   0.5->1(钳)
```

**Blink 把「缩小」钳制在「适配宽度」（=1.0）**，因为页面 viewport 是
`width=device-width, initial-scale=1`，没有 `minimum-scale`。

### 4.2 布局宽度才是真杠杆

| 视口宽 | innerWidth | scrollWidth | 输入区宽 | 字号 |
|---|---|---|---|---|
| 384 | 384 | 384（无横向溢出） | **321 CSS px** | 16px |
| 512 | 512 | 512（无横向溢出） | **449 CSS px** | 16px |
| 768 | 768 | 768（无横向溢出） | **705 CSS px** | 16px |

两件事同时成立：**页面是响应式的**（加宽即重排，无横向溢出），
**但字号恒为 16px**（宿主不随视口缩放字体）。

## 5. 假设判定

| 假设 | 判定 | 依据 |
|---|---|---|
| **H1** 0.75 会被钳制在 1.0 | **成立** | 0.75→1.0，0.9/0.5 同样钳制 |
| **H2** 缩放只能「画小」，不增内容 | **成立（更强）** | 连「画小」都不发生——缩放被钳制，效果为零；且 `scrollWidth` 恒等于视口宽 |
| **H3** 真提升内容量只能加宽 layout viewport | **成立** | 321→449→705 CSS px，且无横向溢出 |
| **H4** 触控目标与缩放无关 | **未完成** | 需真机 `uiautomator dump` 复核（见第 7 节） |

## 6. 决策

1. **不做「0.75 缩放」** —— 它在本页面上不可能生效。已把 `DEFAULT_WEB_ZOOM_PCT` 从 75 改回
   **100**，并在代码注释里写明依据，避免以后有人再把它当成有效开关。
2. **保留缩放能力**（`supportZoom=true`）：放大（>100）确实有效，双指放大是可用的。
3. **「一屏看到更多内容」的正确杠杆是加宽布局视口**，App 侧唯一手段是
   `useWideViewPort=false`（忽略 viewport meta，走 980px 桌面式布局）。
   这属于**观感会明显改变**的改动，且 980px 下字号视觉体积约为当前的 39%，
   需真机确认是否可读——**未实施，待决策**。
4. **布局层的根治仍在上游**：384 px 下输入区只有 321 px，这是宿主响应式布局的结果，
   不是 App 能改的。

## 7. 未完成（诚实标注）

- **A5 真机复核**：本次设备离线（无线调试端口关闭），全部数据来自本机 Chrome 的
  Blink。Android WebView 同为 Blink，钳制规则**预期一致**，但必须在真机上复核：
  1. 装上当前版本，用 `tools/zoom-harness.mjs --attach 127.0.0.1:9222 --skip-nav` 跑一遍；
  2. `uiautomator dump` 取无障碍树，核对触控目标短边（基线 35/35 < 44 CSS px）；
  3. 若真机 `visualViewport.scale` 在请求 0.75 时变成 0.75（与 Blink 结论不符），
     则第 6 节的决策需要推翻重来。
- **A6 第二人复现**：协议已写在本文第 2 节，命令在 `tools/` 里，可直接照跑。

## 8. 复现方式

```bash
TOK=$(journalctl _SYSTEMD_USER_UNIT=dsh-web.service -n 20000 --no-pager \
      | grep -oE 'token=[A-Za-z0-9_-]+' | tail -1 | cut -d= -f2)
node tools/zoom-harness.mjs --url "http://127.0.0.1:3080/?token=$TOK" \
  --width 384 --height 832 --dpr 3.75 --scales "1,0.75,1.25,1.5" --out /tmp/z.json
python3 tools/check-zoom-metrics.py --dir /tmp
```
